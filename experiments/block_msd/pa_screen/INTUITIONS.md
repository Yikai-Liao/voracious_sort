# Pa：深偏斜与跨配置优化的几个直觉

日期：2026-10-18（UTC+08:00）

> 这是对现有现象的结构性猜想，不是一份完整实验方向建议或实施计划。没有新增实测，也不承诺这些改动会提速。

## 先把当前判断说准

Pa 已经展示出很强的竞争力，但“百万条、B=64 全部领先”只适用于此前展示的那组结果。后来补充的纯 u16 已经构成反例，不能把前一句扩展成普遍结论。

以下均为用户报告，比较对象为稳定 MSD：

| 输入／配置 | Pa | 稳定 MSD | Pa 耗时比 |
|---|---:|---:|---:|
| 262,144 条，全等 u128 | 0.79 ms | 0.29 ms | 2.72 倍 |
| 大记录随机输入，B=512 | 255.7 ms | 221.4 ms | 1.155 倍 |
| 百万条，纯 u16 随机 | 9.41 ms | 6.98 ms | 1.348 倍 |
| 百万条，u16 随机 key，带身份信息的 8B 记录 | 14.33 ms | 15.81 ms | 0.906 倍 |

这些现象提示，记录宽度、终结成本和分块参数可能改变优劣关系；它们还不足以定位具体代码原因。此前较早原型的 Pa/Fa 截图也不宜混成当前版本的性能结论。

本轮核对的公开研究分支仍是 [34080cf 基线](https://github.com/Yikai-Liao/voracious_sort/tree/34080cf0fb95355411e029046e026b5aa65fb68c)，没有本次最新 Pa/Fa 实现可供审查。下面的判断都带着这个限制；概念背景沿用此前《Block MSD / LSD 单线程优化方案：结合 RadSort 论文后的修订》。

## 1. 主线直觉：让大群记录更早退出重复处理

Pa 的优势值得保留。直觉上，深偏斜的痛点不是“有没有分桶”，而是分桶以后，几乎同一大群记录是否又进入下一轮扫描、分类、搬运和整理。

一种可能的形态是：普通节点继续使用 Pa；已经观察到的大子桶，再考虑局部使用 Fa 的长路径出口划分。这样复杂分类只出现在它可能减少重复工作的地方，也覆盖“大量 key 共享长前缀、但完整 key 全部不同”的情况。

但这还不是一个选择规则。前面已经完成的 Pa 分布是沉没成本，不能在收益账上抹掉；看到一次大子桶，也不能推出后面还有很多层大子桶。下一轮可能恰好就能快速分开，提前换 Fa 反而多付准备与分类成本。

另外，Boyer–Moore 找的是完整 key 的多数候选，不是重前缀的代表。全部 key 不同时，它可能给出离群候选。若沿用 Fa，代表值如何获得，仍是这条直觉里没有解决的部分。

从区间顺序看，真正的中位数有一个吸引人的性质：Fa 的非终结分组都在它的一侧，因此不会超过节点的一半。但求精确中位数本身也有成本；采样中位数只能提供概率上的代表性，不能继承这个确定性保证。这更像是在提示“代表值的排序位置可能比完整 key 的投票结果重要”，尚不足以决定具体取法。无论选什么值，排序正确与分组足够均衡都应分开理解。

## 2. 想减少的，应当是实际重复工作

沿一条路径，若节点规模依次为 $m_0,m_1,\ldots,m_{h-1}$，反复处理的记录规模是 $\sum_j m_j$。只有确实满足每步 $m_{j+1}\le\rho m_j$、且固定 $\rho<1$，才有

$$
\sum_{j=0}^{h-1}m_j\le m_0\frac{1-\rho^h}{1-\rho}.
$$

当 $\rho$ 接近 1，这个上界依然很大。一次观测不能证明以后都满足这个条件。这个式子也只计算一条路径，不能当成整棵递归树的总成本；其他子桶仍然要排序。

更贴近运行时间的直觉是，把三笔账分开：key 提取、候选选择和 label 计算；实际 scatter 的记录字节；compact、尾块与叶子处理。每个宏节点可能有多个 label pass，因此少一个节点不等于少一次搬运。Fa 只有减少的后续工作覆盖新增成本，才可能值得用。

## 3. 完整重复值是一个清晰的参照，但不包办深偏斜

如果已经有证据说明某个完整 key 占据很大比例，可以想象只做一次稳定三路分布：小于它、等于它、大于它。中间组立刻结束，两侧继续 Pa。这比给整个节点计算完整长路径编号更简单，也能帮助思考“直接拿走一大群已解决记录”究竟值多少。

它不是全等输入的处理方式：全等如果能在必要扫描中证明，应直接结束，没必要再分三路。它也解决不了多数前缀下全为不同 key 的情况。

Boyer–Moore 最终票数 $c$ 是候选真实频数的下界；但一个真实多数也可能只留下较小票数。使用它要区分“已证实能移除多少”与“猜测存在多少”，候选准备、验证以及分布本身也都不是免费工作。

## 4. 全等输入：尽早拿到终结证明

若实现已经扫描 key，并累计相对参考值的差异 OR，那么结果为零就能证明全等。自然的想法是让这个证明尽可能早地挡住不再需要的 workspace 准备、投票和分布流程。

这里的“早”是指得到完整证明之后，而非看到几个相同样本就返回。也不能为了提前退出另加一次对普通输入很贵的全量扫描。0.79 ms 对 0.29 ms 只说明终结路径仍值得关注，并不证明当前代码遗漏了全等检查，或差距一定来自分配。

## 5. 记录宽度和 B：应当看字节，不只看条数

纯 u16 与 8B 记录的相对结果反转，至少说明固定分类工作与记录搬运成本的比例会变化。key 更轻、记录更小时，准备、分支和桶管理更难摊薄；记录变大后，少搬运的价值又可能上升。这仍是解释候选，不是已经证实的原因。

对既有固定基数结构，缓冲区量级可写成 $256BR$，目录量级约为 $d\,n/B$，其中 $R$ 是记录字节数，$d$ 是目录项大小。增大 B 会减少目录项，却扩大记录缓冲；相同 B 对不同 R 并不代表相同工作集。

因此，B=512 的大记录回退提醒我们考虑字节工作集，但不能直接据此宣布 B 应该取哪个值，也不能忽略实际同时存活的其他空间。

## 6. 稀疏变化位：可选的另一种压缩想法

若已有变化掩码 $V=\bigvee_x(key(x)\oplus reference)$，可以按原有高低位顺序只保留会变化的位。删去对所有记录都相同的位，不会改变 key 的大小关系。

于是，128-bit key 中分散在八个位置的变化，有机会变成一个逻辑 8-bit digit，而不是跨着许多恒定位反复细分。这和只跳过共同高位不同。

代价在于抽取这些位也需要指令；稠密输入不应无条件承担更复杂的打包过程。它是否值得做，取决于减少的实际 pass 能否抵消抽取成本，不能只看逻辑位数更少。

## 暂时的落点

更值得追问的是：哪些信息已经足够证明一批记录可以结束，或者下一步能避免大量重复处理？Pa、局部 Fa、重复值分离和变化位压缩，可以围绕这个问题理解。现在还没有足够证据把它们组合成统一决策，更不应把这些直觉写成已经确定的优化路线。
